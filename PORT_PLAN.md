# Twilight Forest: Forge 1.19.2 → Fabric 1.20.1 Port — Master Plan

**Target stack** (confirmed from `gradle.properties`):
- Minecraft `1.20.1`, Fabric Loader `0.15.11`, Fabric API `0.92.2+1.20.1`
- **Official Mojang mappings (Mojmap)** — the Forge branch was already written against Mojmap via Parchment, so ~120k lines of vanilla calls compile with minimal renaming. Only Forge-specific APIs change.
- Mod version `4.2.0-fabric-port`, mod id `twilightforest`

This document is the project HANDOFF roadmap. Read sections 1–2 before touching code, section 4 before wiring the build, and section 5 before declaring any subsystem "done."

---

## 1. Executive Summary

This is a **large, high-risk port** — Twilight Forest is one of the heaviest content mods in the ecosystem, and the analysis surfaces ~900+ touched files across 14 subsystems. The good news: the Mojmap decision eliminates the single largest mechanical cost (SRG→name remapping of vanilla calls). The bad news: nearly every Forge *abstraction layer* — registration, events, capabilities, networking, config, coremods, datagen — has no drop-in Fabric equivalent and must be re-architected, not translated.

**The 3–4 hardest subsystems (the ones that gate everything and carry the most subtle-bug risk):**

1. **Worldgen** (`high`, ~2–3 weeks, 347 files) — by far the biggest. Code-only biome registration, custom chunk generator / biome source codecs referencing static registries, custom structure/placement types, and all biome modifications done in code (no JSON) must move to Fabric's `BiomeModifications` API + `Registry.register` + datagen-emitted JSON. This is the long pole of the entire project.
2. **Registration System** (`high`, 32 files) — `DeferredRegister`/`RegistryObject` → direct `Registry.register`, plus a custom registry (`DwarfRabbitVariant`) needing `DynamicRegistries`. Everything else depends on this compiling first.
3. **Entity System** (`high`, ~3–4 days, 149 files) — multipart Hydra (Forge `PartEntity`), custom spawn-data packets (`IEntityAdditionalSpawnData`), attribute registration event → `FabricDefaultAttributeRegistry`, spawn eggs.
4. **ASM / Mixins / AT** (`high`, 8 files but 13 injection points) — 7 JS coremods → Mixins, 164-line access transcript → AccessWidener, and the multipart-render coremod is entangled with the entity-system `PartEntity` refactor.

Close behind in risk (not difficulty rank): **Datagen** (`high`, 37 files — completely different provider hierarchy) and **Compat** (`high`, 29 files — Curios→Trinkets is a real rewrite, not a rename).

**Realistic total effort: ~7–10 weeks for one experienced Fabric modder.** Worldgen alone is 2–3 weeks; registration + events + entity + networking + capabilities is another ~3 weeks; datagen + items/blocks + compat + loot + mixins/AT is the remaining ~2–4 weeks. The `trivial` (dispensers) and `medium` subsystems are not the schedule drivers — the four `high` subsystems plus datagen are.

## 2. Recommended Phase Ordering

Each phase lists subsystems, the rationale, and what it unblocks. **Phases 0–1 must come first** — nothing else compiles or runs without the build wired and the registry layer ported.

### Phase 0 — Build skeleton & mappings (prerequisite, ~0.5–1 day)
- Wire `build.gradle`: Fabric Loom, Yarn-off / **Mojmap** mappings, Fabric API `0.92.2+1.20.1`, Loader `0.15.11`.
- Create `fabric.mod.json` with entrypoints: `main`, `client`, `fabric-datagen`, and (later) `jei_mod_plugin`.
- Stand up the `AccessWidener` file (`.accesswidener`) referenced from `fabric.mod.json` — see §4. Convert the 164-line `accesstransformer.cfg` now so subsequent phases can reference widened members.
- **Unblocks:** everything. Until the build resolves and an empty `ModInitializer` launches, no subsystem can be validated.

### Phase 1 — Registration core (`Registration System`, `high`)
- `DeferredRegister`/`RegistryObject` → `Registry.register(BuiltInRegistries.X, id, value)`; convert the custom `DwarfRabbitVariant` registry to a Fabric `DynamicRegistries` listener in the initializer.
- Convert `Registry.X_REGISTRY` constants → `Registries.X` (the 1.19.3 relocation) across all 32 files.
- **Unblocks:** items/blocks, entities, worldgen, block entities, structure types, loot types — every subsystem references `TFBlocks`/`TFItems`/`TFEntities`. Do **not** start any content phase until this compiles. (See §5 on registration *ordering*.)

### Phase 2 — Cross-cutting infrastructure (`Networking` medium, `Capabilities` medium, `Event System` high)
Run these together because they are mutually dependent (capability sync uses networking; events drive capability ticks):
- **Networking first** within the phase: `SimpleChannel` → `ServerPlayNetworking`/`ClientPlayNetworking` with `CustomPayload`; build a small templating helper for the 18 packet classes. Replace `PacketDistributor.TRACKING_ENTITY/PLAYER` with manual player iteration.
- **Capabilities**: 4 capabilities (Shield, Feather Fan, Yeti Throw, Giant Pick) → Fabric **Data Attachment API** (`AttachmentRegistry`) with `Codec`. Three of them sync via the packets just ported; Giant Pick is NBT-only.
- **Events**: annotation handlers → Fabric callbacks; the long tail (`ProjectileImpactEvent`, `LivingTickEvent`, `LivingEquipmentChangeEvent`, `EntityMount/Teleport`) needs Mixins — coordinate with Phase 7.
- **Unblocks:** entity behaviors, item effects, progression/charm logic, and anything that ticks or syncs.

### Phase 3 — Entity System (`high`, ~3–4 days)
- Attributes → `FabricDefaultAttributeRegistry`; spawn eggs → vanilla `SpawnEggItem`; `@OnlyIn`→`@Environment`.
- Custom spawn-data packets (`IEntityAdditionalSpawnData` on ChainBlock, SlideBlock, HydraMortarHead, CubeOfAnnihilation, …) → custom S2C payloads built on the Phase-2 networking layer.
- Multipart Hydra (`PartEntity`) → vanilla 1.20 `getParts()` pattern; **must be coordinated with the `multipart.js` coremod** in Phase 7.
- **Unblocks:** mob spawning during worldgen testing, boss encounters, entity renderers.

### Phase 4 — Worldgen (`high`, ~2–3 weeks) — THE LONG POLE
- Start as early as Phase 3 can spare a parallel track if a second engineer exists; otherwise begin immediately after Phase 3.
- Biome/structure/feature/placement registration → Fabric `Registry.register`; codecs (`ChunkGeneratorTwilight`, `TFBiomeProvider`) rewired to `RegistryKeys`/`RegistryOps` context instead of static `Registry.BIOME_REGISTRY`.
- Code-based biome edits → `BiomeModifications.addProperties(...)`.
- Dimension/biome definitions that must become JSON are emitted by the **datagen** phase — so worldgen and datagen interlock.
- **Unblocks:** an actually-loadable Twilight Forest dimension — the core value of the mod.

### Phase 5 — Content surfaces (`items-blocks` medium 211 files, `Dispenser` trivial, `loot-modifiers` medium)
- Items/blocks: `getBurnTime`→`FuelRegistry`, flammability→`FlammableBlockRegistry`, creative tabs→`FabricItemGroup.builder()`, `IPlantable`/`ToolActions`/`initCapabilities` removed.
- Dispensers: near-zero work (vanilla API), just ensure `init()` runs from the `main` entrypoint early enough.
- Loot modifiers → `LootTableEvents.MODIFY`; split `GiantToolGroupingModifier`'s block-break logic out into a real event handler.
- **Unblocks:** correct in-world item/block behavior; loot.

### Phase 6 — Client render (`client-render` medium) & Datagen (`high`, ~3–4 days, 37 files)
- Client: `EntityRendererRegistry`, `BlockEntityRendererFactories`, `ColorProviderRegistry`, `ModelLoadingPlugin`, `ClientModInitializer`. `DimensionSpecialEffects` registration is Forge-specific — needs a Fabric/Mixin route.
- Datagen: re-platform onto `DataGeneratorEntrypoint`/`FabricDataGenerator.Pack`; rewrite tag providers (`FabricTagProvider`), model providers (`FabricModelProvider`, no `ConfiguredModel`), loot providers, and the `FabricDynamicRegistryProvider` that emits worldgen JSON for Phase 4. Drop `ExistingFileHelper`.
- **Unblocks:** correct visuals; generated assets/data that worldgen and recipes depend on.

### Phase 7 — Mixins / AccessWidener / Config / Compat
- **ASM→Mixins**: convert the 7 coremods (`seed`, `maprendercontext`, `music`, `multipart`, `foliage`, `mount`, `book`). `multipart` depends on Phase-3 entity work; `mount` needs careful `@Inject` on `LocalPlayer.Input`. Finalize the AccessWidener begun in Phase 0.
- **Config**: `ForgeConfigSpec` → hand-rolled POJO + Gson (+ optional Cloth Config GUI); update all 25 consumers; `parseBlock` uses `BuiltInRegistries.BLOCK`.
- **Compat**: Curios→**Trinkets**, JEI (`jei_mod_plugin` entrypoint), TOP→**Jade** (already present), `ForgeRegistries.*`→`Registries.*`. These are optional-dependency gated, so they land last without blocking core.

> **Parallelization note:** With two engineers, Phase 4 (worldgen) should run as a dedicated long-lived track starting right after Phase 1, while the second engineer drives Phases 2→3→5→6. Phase 7 is cleanup/optional and merges last.

## 4. Cross-Cutting Concerns

### 4.1 AccessWidener conversion (do this in Phase 0)
The repo ships `src/main/resources/META-INF/accesstransformer.cfg` — **164 lines** (the analysis cited 71 functional entries: 56 public, 9 public-f, 6 protected). Every entry must be converted to a single `.accesswidener` file (v2 header, `namedmojmap`).

**Critical correctness issue:** the AT entries reference **SRG field/method names** (`f_109472_`, `m_93024_`, etc.) with Mojmap human-readable comments. Because this port uses **Mojmap**, the AccessWidener must use the **Mojmap names from the comments**, not the SRG names. Translation map:
- `public <class> <SRG>`  → `accessible field <ClassDotPath> <mojmapName> <descriptor>`
- `public-f <class> <SRG>` → `accessible` **and** `mutable field …` (the `-f` = make non-final)
- `protected <class> <SRG>` (method/field) → `accessible method|field …`
- Wildcard entries (e.g. `AbstractFurnaceBlockEntity *`) must be expanded to explicit per-member lines — AccessWidener has no `*`.
- Inner classes (`Ghast$GhastLookGoal`, `MoveControl$Operation`, `SuspendedTownParticle` ctor) need the `$`-qualified class and, for constructors, `accessible method <Class> <init> <descriptor>`.

Reference it from `fabric.mod.json`: `"accessWidener": "twilightforest.accesswidener"`. Validate at build time — a malformed AW fails the dev launch loudly, which is the desired early signal.

### 4.2 Mappings rationale (Mojmap)
The Forge branch was already authored against Mojmap (via Parchment). Choosing **official Mojang mappings** for the Fabric port means the ~120k lines of vanilla calls compile with near-zero renaming — the cost collapses to the Forge-abstraction layers only. Configure Loom to use Mojmap (layered mappings: official + optional Parchment for parameter names). **Do not** default to Yarn — it would force a full vanilla-call rename pass that the Mojmap choice exists specifically to avoid.

## 5. Known Sharp Edges (most likely to cause subtle runtime bugs)

These compile fine and then misbehave at runtime. Budget explicit QA for each.

1. **Registration ordering (silent NPEs / empty registries).** Forge `DeferredRegister` deferred everything to the mod bus and resolved ordering for you. Fabric `Registry.register` is eager and runs in entrypoint order, which is *undefined* across entrypoints. Static-field init that references another registry that hasn't run yet yields nulls. **Mitigation:** force all `TFBlocks`/`TFItems`/`TFEntities`/etc. `init()` calls through a single ordered sequence in the `main` `ModInitializer`. The dispenser subsystem flags the same trap — its `init()` must run before resources finish loading.

2. **Capability sync drift on respawn / dimension change / entity conversion.** The Forge capabilities re-attached via `AttachCapabilitiesEvent` and Forge handled copy-on-respawn. Data Attachments do **not** automatically copy across player respawn or `LivingEntity` conversion. Shield/Feather-Fan/Yeti-Throw store live entity references and sync via packets. **Mitigation:** define a copy predicate on the AttachmentType and add explicit re-sync on `ServerPlayerEvents.AFTER_RESPAWN` / dimension-change; verify the shield count survives a death and the feather-fan fall state doesn't leak to a fresh clone.

3. **`PacketDistributor.TRACKING_ENTITY_AND_SELF` semantics.** Hand-rolled player iteration easily forgets "and self," or sends to trackers that haven't started tracking yet. Capability and particle packets are the affected ones. **Mitigation:** centralize a `sendToTrackingAndSelf(entity, payload)` helper and unit-walk every former `PacketDistributor` call site against it.

4. **Multipart entity spawn/parts (Hydra).** Forge `PartEntity` + the `multipart.js` coremod handled both logic and rendering. On Fabric, `getParts()` must be wired to the vanilla 1.20 multipart path **and** the render-side coremod converted to a Mixin in lockstep — a mismatch yields invisible or non-collidable heads. `TFPart.assignPartIDs()` and `IEntityAdditionalSpawnData` on `HydraMortarHead` interact here. **Mitigation:** port the entity `getParts()` and the `multipart` Mixin in the same change; test boss collision *and* visibility in multiplayer (the spawn-data packet only matters client-side under a remote server).

5. **Biome modifiers running code instead of JSON.** All Twilight biome edits are code-based; on Fabric they move to `BiomeModifications.addProperties(selector, modifier)`. Selectors that are too broad will mutate vanilla/overworld biomes; too narrow and Twilight biomes lose features silently. **Mitigation:** scope every selector to the Twilight dimension/biome tag and diff a generated world against the Forge reference for feature presence.

6. **Codecs holding stale static registry references.** `ChunkGeneratorTwilight` and `TFBiomeProvider` `RecordCodecBuilder`s reference `Registry.BIOME_REGISTRY`/`STRUCTURE_SET_REGISTRY` statically. In 1.20.1 these must resolve through `RegistryOps`/`RegistryKeys` from context — a static reference will compile against `BuiltInRegistries` but deserialize against the *wrong* (un-frozen or default) registry, producing missing biomes or crash-on-load. **Mitigation:** route all codec registry lookups through the `RegistryOps` context; test save/reload of a Twilight world.

7. **Loot modifier timing (`GiantToolGroupingModifier`).** Forge GLMs ran *during* the drop; the `BreakEvent` logic baked into this modifier cannot live inside a `LootTableEvents.MODIFY` callback (which is post-generation, table-build time). Leaving it there means the grouping never triggers. **Mitigation:** extract the break-time behavior into a `PlayerBlockBreakEvents.AFTER` handler and keep only static table edits in `LootTableEvents`.

8. **`ForgeHooks.isCorrectToolForDrops` / tool-action gaps.** `ToolActions.SHIELD_BLOCK`, `AXE_WAX_OFF`, and `isCorrectToolForDrops` have no Fabric constant; naive replacements change harvest/shield behavior subtly (e.g., Knightmetal shield not blocking, fiery tools not smelting). **Mitigation:** map each to a concrete vanilla method or tag and behavior-test the specific items (Knightmetal Shield, Giant tools, Fiery tools).

9. **Client `DimensionSpecialEffects` registration is Forge-only.** There is no Fabric API event; this needs a Mixin into the dimension-effects registry. Miss it and the Twilight sky/fog renders as overworld. **Mitigation:** verify sky color, fog, and cloud behavior in-dimension after the client phase.

10. **AccessWidener SRG→Mojmap name mismatch (silent build-time, see §4.1).** Converting AT entries by copying the SRG token (`f_109472_`) into the AccessWidener will fail to widen anything under Mojmap — and the dependent Mixin/render code then crashes at runtime with `IllegalAccessError`. **Mitigation:** convert using the Mojmap names from the AT comments, expand wildcards explicitly, and confirm each widened member is actually reachable from the code that needs it.

---

**First three concrete steps for the next engineer:** (1) wire Phase 0 build + Mojmap Loom + the converted AccessWidener and get an empty client to launch; (2) port Phase 1 registration and confirm `TFBlocks`/`TFItems` resolve with no null statics; (3) begin the Phase 4 worldgen track in parallel — it is the 2–3 week long pole and should not wait on the medium-difficulty content phases.
